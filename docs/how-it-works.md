# How Fan Control works

For developers and the curious. For what Fan Control does, see the [README](../README.md).

## Pieces

| Piece | Runs as | Where |
|---|---|---|
| `plugin.json`, `main.js`, `backend.py` | the user, inside Framey | `~/frame-fan`, linked as `~/framey/plugins/fan` |
| `fan-apply.py` | root | `/etc/frame-fan/fan-apply.py` |
| patched `fancontrol.py` and config | root | `/etc/frame-fan/fan/` |
| `frame-fan.path`, `frame-fan.service`, `frame-fan-stock.service` | systemd | `/etc/systemd/system/` |
| drop-in for `deckard-fan-control` (exists only while a custom profile is active) | systemd | `/etc/systemd/system/deckard-fan-control.service.d/frame-fan.conf` |

## Flow

1. The page calls the backend (`Framey.call("fan", "set", ...)`). The backend validates the request and writes `~/.config/frame-fan/fan.json` (to a temporary file in the same folder, then renamed over it, so a cut-off write cannot leave a truncated file; the backend does the same for the saved profiles).
2. `frame-fan.path` notices the change and starts `frame-fan.service`, which runs `/etc/frame-fan/fan-apply.py` as root.
3. The script validates the request again, rebuilds the config from Valve's stock files, patches a copy of Valve's `fancontrol.py` and syntax-checks it, writes the systemd drop-in, restarts `deckard-fan-control`, which now runs the copy from `/etc/frame-fan`, waits about 3 seconds and checks that the service is still active with an unchanged restart count, and only then writes `applied.json` (the stock and error records above are the only other writes). If any step fails, including that check, it goes back to stock instead. The whole script runs under a lock (see below). A request that fails validation is rejected with exit status 1 and nothing changes.
4. The page reads `applied.json`, the fan's hwmon files and Valve's temperature sensors to show what is active. It shows a selected profile as active only once `applied.json` changes (or after 15 seconds, whichever comes first), so a rejected or failed request does not stay highlighted.

A request is either `{"stock": true}`, a ramp (`floor`, `ceil`, `t0`, `t1`, `s`), or `{"points": [[temp, pwm], ...]}` with six or seven points. Saved profiles live in `~/.config/frame-fan/fan-profiles.json`, at most eight. The backend re-validates what it reads: a file that is not a list, or entries that are malformed or no longer valid, are ignored instead of breaking the page, and an `applied.json` that is not a valid record is shown as stock.

## Validation rules

PWM is 30 to 98. Ramp: `30 <= floor <= ceil <= 98`, `t0 >= 25`, `t0 + 5 <= t1 <= 90`, `-100 <= s <= 100`. Points: six or seven, temperatures 25 to 90 at least 2 degrees apart, PWM never decreasing as temperature rises, and the curve, interpolated the way the controller does it, at 80 °C or more of PWM 78 (about 80%). The same rules are in `backend.py` and `fan-apply.py`. Whatever the profile, the patched controller also never commands less than PWM 78 while a sensor reads 80 °C or more, so a ramp or constant profile with a lower maximum is raised to 78 from 80 °C. The request file is read only if it is a regular file of at most 64 KB and not a symlink.

## The patched controller

`fan-apply.py` rebuilds `/etc/frame-fan/fan/fancontrol.py` from Valve's original on every apply by making a small set of exact-string edits and aborting if an expected anchor is missing. The edits add a `custom()` method that gives the commanded speed as a function of the filtered control temperature only, the 80 °C floor, an exit once more than 20 consecutive temperature reads of one sensor have failed (the counter is cleared at the point where Valve's loop resets its poll counter), and a start value for a sensor's temperature (see below). The result is compiled before use, and the YAML substitutions must each match the expected number of lines. The emergency behavior at Valve's maximum temperature (95 °C, or the sensor's own critical value if it is between 60 and 95) is left alone, and the `fan_max_speed` attribute it reads is kept (the earlier public version lost it; see "Fixed in 1.0" in the README).

`custom()` has two forms. For a graph profile it is the piecewise-linear interpolation of the points (flat before the first and after the last). For a ramp or constant profile it is `floor + (ceil - floor) * ((1 - k) * x + k * x * x)` rounded to an integer, with `k = s / 100` and `x = (T - t0) / (t1 - t0)` clamped to 0 to 1. So the speed is the floor up to `t0`, the ceiling from `t1`, and never decreases in between for any `s` from -100 to 100 (the slope in `x` is `(1 - k) + 2 * k * x`, which is not negative on 0 to 1). Valve's own controller type for these devices (`ffquad`) still runs, but its output, which includes a term for the power drawn on the VPH rail, is no longer used: every custom mode, like graph mode, depends on temperature only. Stock keeps that term.

The config is rebuilt from Valve's stock file: `fan_min_speed` is the profile's floor (the first point's PWM for a graph), `fan_charging_min_speed` is the floor plus 5 capped at the maximum, `fan_max_speed` is 98 and `fan_hysteresis` is 6. Each device entry gets one extra line, `ramp: [floor, ceil, t0, t1, s/100]` or `curve: [[temp, pwm], ...]`. `T_threshold` is left at Valve's 45; the controller uses it only as the value for an overflow reading of 255 °C or more, as in stock.

If a sensor cannot be read when the controller starts (this includes the `--stop` run that systemd does after the service stops), its temperature starts at the device's `max_temp` (95), so the loop commands maximum and `--stop` goes on to its normal step of setting the fan to maximum, instead of failing with an `AttributeError` after the fan constructor has already written the floor. After more than 20 consecutive failed reads of one sensor in the loop, the process exits and systemd runs `--stop`, which now sets maximum. A sensor that has never been read since start-up is assumed to be at the limit; a sensor that worked and then fails keeps its last good value for the 20 reads. Valve's unmodified controller, which runs after a switch to stock, still crashes in the same situation and leaves its own minimum.

Valve's files this was checked against (SteamOS 0.4.5, copies read from a headset): `fancontrol.py` sha256 `35f47241d76977f9966e0292d3e3cbdd072c753a21ceb63336f5d74b81910b65`, `deckard-config.yaml` `43735f74690189d4e8b942f119a0ab3623f05e3ef940d7506da041635c0ff73c`, `PID.py` `7a2de377b0de560d5df4cdd863d7b5a10d08cd8e1ba8ca28efed4c7a2f464df3`. A different Valve version is not covered by that check, though the exact-anchor rule makes a changed layout fall back to stock instead of patching blindly.

## Failure recovery

The drop-in sets `OnFailure=frame-fan-stock.service` with `StartLimitIntervalSec=20` and `StartLimitBurst=10`. When the fan service fails, that unit runs `fan-apply.py --stock`, which deletes the drop-in so the service runs Valve's own unmodified controller and config, clears the failed state, restarts the service and records `{"stock": true, "fallback": true}`. A stock choice made in the page records `{"stock": true}` instead. This covers a bug in the patched controller too, but not a bug in `fan-apply.py` itself. After removing the drop-in and reloading systemd, and just before the restart, it writes PWM 98 to the fan's `pwm1` and reads it back. If the hwmon device is not found or the write or read-back fails, the restart still goes ahead, the failure is printed to stderr (the journal) and `"max": false` is added to the record, for example `{"stock": true, "max": false, "fallback": true}`; the page shows it as "Maximum fan write failed before stock restart". A successful write adds nothing to the record. Any other failure in this path (for example the reload or the restart) is an error. The restart gets the same 3 second stability check as an apply, and if the restart fails or the service is not stable, `applied.json` records `{"stock": true, "error": true}` (plus `"max": false` if the write had already failed), which the page shows as "Fan service failed to restart". The maximum write only covers the switch itself: Valve's stock stop step rewrites the fan speed to its own maximum (55) and its start step to its minimum within about a second, after which Valve's controller sets the speed. Every `systemctl` call in the script has a 30 second timeout, so a hung systemctl ends in the error record instead of holding the lock forever.

## Locking

`fan-apply.py` (apply, `--stock` and the failure recovery) takes an exclusive `flock` on `/run/frame-fan.lock`, retrying for up to 60 seconds. If it cannot get the lock, an apply exits with status 1 and changes nothing, but `--stock` (the failure recovery) carries on without the lock, so a stuck run cannot stop the fallback. A queued apply that runs after the uninstall has removed `/etc/frame-fan/fan` exits quietly without touching anything. `install-root.sh` and `uninstall-root.sh` re-run themselves under `flock -w 60` on the same file and set `FRAME_FAN_LOCKED=1`, which makes the scripts they call (including each other) skip taking it again. `/run` is root-owned and cleared on reboot.

## Hardware notes

The fan is the hwmon device named `slg4ax46073v`, found by name rather than index. The commanded percentage shown is `pwm * 100 / 98`.

The temperature shown comes from the same 13 hwmon nodes Valve's config lists (`cpu7_middle_thermal`, `cpu0_thermal`, `cpu1_thermal`, `cpu2_bottom_thermal` to `cpu6_bottom_thermal`, `gpuss_0_thermal` to `gpuss_4_thermal`), found by their `name` file, each read from `temp1_input` in millidegrees. The page shows the hottest one with one decimal and its name. It is the instantaneous reading, while Valve's controller averages five samples taken 0.2 seconds apart and keeps its last peak until the average falls by more than 1 °C, so the displayed value can lag or lead the control input slightly. Unreadable or missing nodes are skipped. Only if none of the 13 exist does it fall back to the earlier scan of `/sys/class/thermal/thermal_zone*` for types starting with `cpu` or `gpuss`. Whether the hwmon names on the headset equal the names in the config was not observed (the headset was unreachable); it follows from Valve's controller finding those sensors by the same names. The measured percentage divides the tachometer reading by an assumed 172 rpm per percent, a calibration from one headset, so treat it as approximate.

## Privilege boundary

The running pieces root executes (`fan-apply.py`, the patched controller and config, the units and the drop-in) live in `/etc/frame-fan` and `/etc/systemd/system`, owned by root and not writable by the user. The only user-writable input they read is `fan.json`, read as data and range-checked.

The install-time scripts are different. `install-root.sh`, `uninstall-root.sh` and `selftest-root.sh`, and the source of `fan-apply.py` that the install copies into `/etc/frame-fan`, stay in `~/frame-fan`, a folder the user (and any plugin running as that user) can write. The Framey App performs install, update and removal by running them through `sudo` from that folder, and `install-root.sh`'s failure trap runs `/home/steamos/frame-fan/uninstall-root.sh` as root. So whatever is in those files when the headset password is entered runs as root, and a file changed in between would run as root and, in the case of `fan-apply.py`, persist in `/etc/frame-fan`. This is a trust boundary that is not enforced here, only documented.

## Scripts

- `install-root.sh` (locked, `set -e`): stops the path watcher, removes any old drop-in, copies Valve's `deckard-fan-control` directory to `/etc/frame-fan/fan`, installs `fan-apply.py`, makes `/etc/frame-fan` root-owned and not group/other writable, writes the three units, then applies the current settings if `fan.json` exists (otherwise restarts stock and records `{"stock": true}`). If applying them exits with an error because the file is stale or invalid, it runs `fan-apply.py --stock` instead, which records `{"stock": true, "fallback": true}`, and the install carries on; only a failing stock hand-over rolls the install back. It waits 15 seconds, requires `deckard-fan-control` to be active, enables the path watcher last and prints the fan RPM and `applied.json`. On any failure it runs the uninstall script as a rollback. If applying the saved settings falls back to stock successfully, the install still completes, with the fallback flag recorded. Paths are hard-coded to `/home/steamos/frame-fan`.
- `uninstall-root.sh` (locked, `set -e`): disables the path watcher, removes the units and the drop-in, reloads systemd, restarts the stock service, waits 3 seconds, requires it to be active, and removes `/etc/frame-fan` last. It stops at the first failing step, so a failure before the end leaves `/etc/frame-fan` in place. It does not touch `~/.config/frame-fan`.
- `selftest-root.sh` (not locked itself): refuses to run unless it is root, `applied.json` exists and is a custom profile, and exactly one fan hwmon device is found. It then sends SIGKILL to the fan service 16 times at 1.4 second intervals to check the fallback, and checks that the fallback was recorded, the service is active, the unit no longer mentions `frame-fan` and `pwm1` is readable. An exit trap (also on interrupt) clears the failed stock unit, reruns `fan-apply.py` and checks that the profile and an active service were restored. Each check prints `ok:` or `FAIL:`; the script ends with `PASS` and exit status 0, or `FAIL` and status 1 if any check failed or it was interrupted. It was checked only with stubbed commands, never on a headset.
