# How Fan Control works

For developers and the curious. For what Fan Control does, see the [README](../README.md).

## Pieces

| Piece | Runs as | Where |
|---|---|---|
| `plugin.json`, `main.js` | the user, inside Framey | `~/frame-fan`, linked as `~/framey/plugins/fan` |
| `backend.py` | the user, in a worker process started by Framey | same folder |
| `fan-apply.py` | root | `/etc/frame-fan/fan-apply.py` |
| patched `fancontrol.py` and config | root | `/etc/frame-fan/fan/` |
| `frame-fan.path`, `frame-fan.service`, `frame-fan-stock.service` | systemd | `/etc/systemd/system/` |
| drop-in for `deckard-fan-control` (exists only while a custom profile is active) | systemd | `/etc/systemd/system/deckard-fan-control.service.d/frame-fan.conf` |
| `update-helper`, `root-lib.sh`, `allowed_signers`, version marker `.version` | root | `/etc/frame-fan/` |
| sudo rule for the helper | sudo | `/etc/sudoers.d/frame-fan-update` |
| update backup | root | `/var/lib/frame-fan/backup` (mode 0700) |

## Flow

1. The page calls the backend (`Framey.call("fan", "set", ...)`). The backend validates the request and writes `~/.config/frame-fan/fan.json` (to a temporary file in the same folder, then renamed over it, so a cut-off write cannot leave a truncated file; the backend does the same for the saved profiles).
2. `frame-fan.path` notices the change and starts `frame-fan.service`, which runs `/etc/frame-fan/fan-apply.py` as root.
3. The script validates the request again, rebuilds the config from Valve's stock files, patches a copy of Valve's `fancontrol.py` and syntax-checks it, writes the systemd drop-in, restarts `deckard-fan-control`, which now runs the copy from `/etc/frame-fan`, waits about 3 seconds and checks that the service is still active with an unchanged restart count, and only then writes `applied.json` and the throttle stamp `/run/frame-fan.stamp` (the stock and error records above are the only other writes to `applied.json`). If any step fails, including that check, it goes back to stock instead. The whole script runs under a lock (see below). A request that fails validation is rejected with exit status 1 and nothing changes.
4. The page reads `applied.json`, the fan's hwmon files and Valve's temperature sensors to show what is active. It shows a selected profile as active only once `applied.json` changes (or after 15 seconds, whichever comes first), so a rejected or failed request does not stay highlighted.

A request is either `{"stock": true}`, a ramp (`floor`, `ceil`, `t0`, `t1`, `s`), or `{"points": [[temp, pwm], ...]}` with six or seven points. Saved profiles live in `~/.config/frame-fan/fan-profiles.json`, at most eight. The backend re-validates what it reads: a file that is not a list, or entries that are malformed or no longer valid, are ignored instead of breaking the page, and an `applied.json` that is not a valid record is shown as stock.

## Validation rules

PWM is 30 to 98. Ramp: `30 <= floor <= ceil <= 98`, `t0 >= 25`, `t0 + 5 <= t1 <= 90`, `-100 <= s <= 100`. Points: six or seven, temperatures 25 to 90 at least 2 degrees apart, PWM never decreasing as temperature rises, and the curve, interpolated the way the controller does it, at 80 °C of PWM 78 or higher. The same rules are in `backend.py` and `fan-apply.py`. Whatever the profile, the patched controller also never commands less than PWM 78 while a sensor reads 80 °C or more, so a ramp or constant profile with a lower maximum is raised to 78 from 80 °C. The request file is read only if it is a regular file of at most 64 KB and not a symlink.

## The patched controller

`fan-apply.py` rebuilds `/etc/frame-fan/fan/fancontrol.py` from Valve's original on every apply by making a small set of exact-string edits and aborting if an expected anchor is missing. The edits add a `custom()` method that gives the commanded speed as a function of the filtered control temperature only, the 80 °C floor, an exit once more than 20 consecutive temperature reads of one sensor have failed (the counter is cleared at the point where Valve's loop resets its poll counter), and a start value for a sensor's temperature (see below). The result is compiled before use, and the YAML substitutions must each match the expected number of lines. The emergency behavior at Valve's maximum temperature (95 °C, or the sensor's own critical value if it is between 60 and 95) is left alone, and the `fan_max_speed` attribute it reads is kept.

`custom()` has two forms. For a graph profile it is the piecewise-linear interpolation of the points (flat before the first and after the last). For a ramp or constant profile it is `floor + (ceil - floor) * ((1 - k) * x + k * x * x)` rounded to an integer, with `k = s / 100` and `x = (T - t0) / (t1 - t0)` clamped to 0 to 1. So the speed is the floor up to `t0`, the ceiling from `t1`, and never decreases in between for any `s` from -100 to 100 (the slope in `x` is `(1 - k) + 2 * k * x`, which is not negative on 0 to 1). Valve's own controller type for these devices (`ffquad`) still runs, but its output, which includes a term for the power drawn on the VPH rail, is no longer used: every custom mode, like graph mode, depends on temperature only. Stock keeps that term.

The config is rebuilt from Valve's stock file: `fan_min_speed` is the profile's floor (the first point's PWM for a graph), `fan_charging_min_speed` is the floor plus 5 capped at the maximum, `fan_max_speed` is 98 and `fan_hysteresis` is 6. Each device entry gets one extra line, `ramp: [floor, ceil, t0, t1, s/100]` or `curve: [[temp, pwm], ...]`. `T_threshold` is left at Valve's 45; the controller uses it only as the value for an overflow reading of 255 °C or more, as in stock.

If a sensor cannot be read when the controller starts (this includes the `--stop` run that systemd does after the service stops), its temperature starts at the device's `max_temp` (95), so the loop commands maximum and `--stop` goes on to its normal step of setting the fan to maximum, instead of failing with an `AttributeError` after the fan constructor has already written the floor. After more than 20 consecutive failed reads of one sensor in the loop, the process exits and systemd runs `--stop`, which now sets maximum. A sensor that has never been read since start-up is assumed to be at the limit; a sensor that worked and then fails keeps its last good value for the 20 reads. Valve's unmodified controller, which runs after a switch to stock, still crashes if a sensor cannot be read at start-up and leaves its own minimum. During a run it keeps the last value it read and does not exit.

Valve's files this was checked against (SteamOS 0.4.5, copies read from a headset): `fancontrol.py` sha256 `35f47241d76977f9966e0292d3e3cbdd072c753a21ceb63336f5d74b81910b65`, `deckard-config.yaml` `43735f74690189d4e8b942f119a0ab3623f05e3ef940d7506da041635c0ff73c`, `PID.py` `7a2de377b0de560d5df4cdd863d7b5a10d08cd8e1ba8ca28efed4c7a2f464df3`. A different Valve version is not covered by that check, though the exact-anchor rule makes a changed layout fall back to stock instead of patching blindly.

## Failure recovery

The drop-in sets `OnFailure=frame-fan-stock.service` with `StartLimitIntervalSec=20` and `StartLimitBurst=10`. When the fan service fails, that unit runs `fan-apply.py --stock`, which invalidates the success stamp and deletes the drop-in so the service runs Valve's own unmodified controller and config, clears the failed state, restarts the service and records `{"stock": true, "fallback": true}`. A stock choice made in the page records `{"stock": true}` instead. This covers a bug in the patched controller too, but not a bug in `fan-apply.py` itself. After removing the drop-in and reloading systemd, and just before the restart, it writes PWM 98 to the fan's `pwm1` and reads it back. If the hwmon device is not found or the write or read-back fails, the restart still goes ahead, the failure is printed to stderr (the journal) and `"max": false` is added to the record, for example `{"stock": true, "max": false, "fallback": true}`; the page shows it as "Maximum fan write failed before stock restart". A successful write adds nothing to the record. Any other failure in this path (for example the reload or the restart) is an error. The restart gets the same 3 second stability check as an apply, and if the restart fails or the service is not stable, `applied.json` records `{"stock": true, "error": true}` (plus `"max": false` if the write had already failed), which the page shows as "Fan service failed to restart". The maximum write only covers the switch itself: Valve's stock stop step sets the fan to its own maximum (55) and its start step to its minimum shortly afterwards (not measured on a headset), after which Valve's controller sets the speed. Every `systemctl` call in the script has a 30 second timeout, so a hung systemctl ends in the error record instead of holding the lock forever.

## Locking

`fan-apply.py` (apply, `--stock` and the failure recovery) takes an exclusive `flock` on `/run/frame-fan.lock`, retrying for up to 60 seconds. If it cannot get the lock, an apply exits with status 1 and changes nothing, but `--stock` (the failure recovery) carries on without the lock, so a stuck run cannot stop the fallback. A queued apply that runs after the uninstall has removed `/etc/frame-fan/fan` exits quietly without touching anything. `install-root.sh` and `uninstall-root.sh` re-run themselves under `flock -w 60` on the same file and set `FRAME_FAN_LOCKED=1`, which makes the scripts they call (including each other) skip taking it again. `/run` is root-owned and cleared on reboot.

## Hardware notes

The fan is the hwmon device named `slg4ax46073v`, found by name rather than index. The commanded percentage shown is `pwm * 100 / 98`.

The temperature shown comes from the same 13 hwmon nodes Valve's config lists (`cpu7_middle_thermal`, `cpu0_thermal`, `cpu1_thermal`, `cpu2_bottom_thermal` to `cpu6_bottom_thermal`, `gpuss_0_thermal` to `gpuss_4_thermal`), found by their `name` file, each read from `temp1_input` in millidegrees. The page shows the hottest one with one decimal and its name. It is the instantaneous reading, while Valve's controller averages five samples taken 0.2 seconds apart and keeps its last peak until the average falls by more than 1 °C, so the displayed value can lag or lead the control input slightly. Unreadable or missing nodes are skipped. Only if none of the 13 can be read does it fall back to the earlier scan of `/sys/class/thermal/thermal_zone*` for types starting with `cpu` or `gpuss`. Whether the hwmon names on the headset equal the names in the config was not observed (the headset was unreachable); it follows from Valve's controller finding those sensors by the same names. The measured percentage divides the tachometer reading by an assumed 172 rpm per percent, a calibration from one headset, so treat it as approximate.

## Backend process

The loader runs `backend.py` in a separate worker process (one per plugin, started on the first call, stopped after `backend.idle` seconds without one, 120 by default). The manifest sets `"backend": {"timeout": 10, "idle": 120}`: a call that runs longer than 10 seconds is abandoned and the worker is pinged, and killed when it does not answer. The worker is started with `NO_NEW_PRIVS`, an allowlisted environment, lowered priority, limits on core dumps, open files, file size and data memory (32 MB unless the manifest sets `memory_mb`, which Fan Control's does not), and its standard output is reserved for the loader's protocol, so a `print` would go to the journal instead of the reply. It is failure containment, not a security sandbox: the worker is the same user and can read that user's files.

What that means for this backend, which was written before the worker existed and was not changed for it: it does not print, does not call `sudo` or anything setuid (which `NO_NEW_PRIVS` would refuse), keeps no background task or thread between calls (each call reads the sysfs files, `applied.json` and the saved profiles again), and writes only `fan.json` and `fan-profiles.json` in `~/.config/frame-fan`. That folder is not the per-plugin config folder the loader offers other plugins: it stays where it is because the root path unit watches `fan.json`, and nothing is moved. A crashing or hung backend leaves the page showing an error and the root parts untouched: they run from systemd, not from the worker.

The loader and its workers (at most 3, the loader's `MAX_WORKERS`) share the one 150 MB limit of the Framey service (`MemoryMax=150M`, as set in the unit the Framey App writes). Tested on Windows with the loader's own supervisor and a fake sysfs; the Linux-only parts (`NO_NEW_PRIVS`, limits, process-group kill) have not run with this backend, and nothing was measured on a headset.

## Updates

`/etc/frame-fan/update-helper` is `update-helper.sh` from this repository, installed root-owned. The sudo rule lets the `steamos` user run only `update-helper update` and `update-helper rollback`, without a password. The helper refuses any other argument with exit status 2 and acts only when run through sudo by `steamos` as root (`SUDO_USER` must be `steamos`). It clears its environment, pins `PATH=/usr/bin:/bin`, uses `umask 077`, sets the core-dump limit to 0 and the file-size limit to unlimited (and refuses to run if it cannot), and takes its repository, asset names, signer identity, namespace and trust file from constants in the script.

`update`, in order:

1. Take the shared lock (`/run/frame-fan.lock`, up to 60 seconds).
2. Fetch the latest release metadata from `api.github.com/repos/chaosfox26/frame-fan/releases/latest` over HTTPS. Require exactly one asset named `frame-fan.tar.gz` and one named `frame-fan.tar.gz.sig`. Each asset URL must use HTTPS on the default port, a host in `github.com`, `api.github.com`, `objects.githubusercontent.com` or `release-assets.githubusercontent.com`, and a path starting `/chaosfox26/frame-fan/`.
3. Download both into a fresh root-only temporary directory. Cap the tarball at 4 MiB and the signature at 4 KiB.
4. Require `/etc/frame-fan/allowed_signers` to be a root-owned regular file not writable by group or other. Verify the signature with `ssh-keygen -Y verify`, identity `framey-release`, namespace `framey-fan-release`.
5. Validate the tar listing with Python's `tarfile` before extracting. Accept only plain files and directories under `frame-fan/`, with names made of letters, digits, dots, underscores and hyphens. Refuse absolute paths, `.` or `..` components, links, devices, fifos, duplicate paths, paths deeper than 8 components, more than 300 entries or more than 8 MiB in total.
6. Extract with `--no-same-owner --no-same-permissions`. Check again that the extracted tree contains only directories and plain files with no hard links.
7. Require `plugin.json` with id `fan` and a three-number version strictly greater than `/etc/frame-fan/.version`. Equal means "already current", exit 0 with no installation; a lower version is refused.
8. Syntax-check the new `root-lib.sh`, `update-helper.sh` and `fan-apply.py`. Write the current root-side files (`/etc/frame-fan`, the three units, the drop-in, the sudo rule) as one tar to `/var/lib/frame-fan/backup.new`. Save the completed archive's member listing as `members` and its whole-file SHA-256 digest as `sha256` in the same root-owned backup directory. Sync the archive, listing and digest. Recompute the digest and compare it with `sha256`, then list the archive again and compare the names with `members`. This checks the completed archive against its recorded digest and member list; it does not compare file contents with the original source tree. Only then remove the old `/var/lib/frame-fan/backup` and move the new one into place. If the new backup fails the check, nothing is changed and the old backup stays.
9. Source the new `root-lib.sh` from the verified copy and run its `ff_install`, including activation and the active-service check described below. Write the marker last, by atomic rename.

The backup stays after a successful update so `rollback` has something to restore, and is replaced by the next update.

From inside the headset the loader drives this from Framey's Modules page (Update on the Fan Control card, or Update all). Its side, in order: look up the latest release of `chaosfox26/frame-fan`; refuse unless the tag is newer than the installed `plugin.json` version; download `frame-fan.tar.gz` and its `.sig` from `github.com`; if GitHub published a `sha256:` digest for the tarball, refuse on a mismatch (nothing is compared when no digest, or another algorithm, is published); verify the signature with `ssh-keygen -Y verify` against `/etc/frame-fan/allowed_signers`, which must be root-owned; unpack into a staging folder and require the same plugin id, a newer version, the `privileged` declaration and a passing compatibility check (`framey`, `platform`, `api`); swap the user-level files in; run `sudo -n /etc/frame-fan/update-helper update`; and require `/etc/frame-fan/.version` to equal the new version. A failure before the helper runs restores the previous files. A failure after the swap leaves a partial update that the card shows with **Retry protected step**, **Check again** and **Restore previous version**. The helper repeats its own download and signature check; it does not use the digest.

`ff_install` and `ff_activate` live in `root-lib.sh`, which the one-time install and the helper share. `ff_install` is the old body of `install-root.sh` (stop the path watcher, remove the drop-in, copy Valve's files, install `fan-apply.py`, the helper and the library, write the units, write and validate the sudo rule, then `ff_activate`: reload systemd, apply the saved settings or restart stock, wait 15 seconds, require `deckard-fan-control` to be active, enable the path watcher). It does not touch `allowed_signers`.

If any step after the backup fails (including a signal), the exit handler first checks the backup's whole-file digest and member list again. Missing, truncated, changed or legacy backups without a digest are refused before any live files are removed. A verified restore invalidates the throttle stamp, removes the current files, unpacks the backup, sources the restored `root-lib.sh` and runs `ff_activate`. The digest detects accidental archive corruption, including same-length payload damage with valid tar headers; an attacker who controls the root-owned archive and digest can replace both. If even that fails, it removes the drop-in and restarts Valve's stock service; if that stock service is not active, the helper prints `stock fallback failed: deckard-fan-control is not active` to stderr. INT, TERM and HUP are trapped in the helper and exit through the same handler. The marker is not written on any failure path. `rollback` is the restore step on its own, with no network access; it deletes the backup after succeeding, and refuses (exit 1) when there is none. The helper never writes under `/home/steamos`.

The one-time `install-root.sh` requires `--signer-fp SHA256:...`, reads `release-signing/allowed_signers` once, requires it to be exactly one line with principal `framey-release`, namespace `framey-fan-release` and an `ssh-ed25519` key, requires that key's `ssh-keygen -lf` fingerprint to equal the argument, and only then writes `/etc/frame-fan/allowed_signers`, through a temporary file that is synced and renamed over the old one. It writes the version marker from `plugin.json` after `ff_install`. See [release-signing.md](release-signing.md) for signing, key custody and limits.

## Privilege boundary

The running pieces root executes (`fan-apply.py`, the patched controller and config, the units and the drop-in) live in `/etc/frame-fan` and `/etc/systemd/system`, owned by root and not writable by the user. The only user-writable input they read is `fan.json`, read as data and range-checked.

After the one-time install, update code comes only from a release whose signature was verified against the root-owned trust file, unpacked in a root-only directory, and the helper itself is root-owned. The install-time scripts are different. `install-root.sh`, `root-lib.sh`, `uninstall-root.sh` and `selftest-root.sh`, and the source of `fan-apply.py` and `update-helper.sh` that the one-time install copies into `/etc/frame-fan`, stay in `~/frame-fan`, a folder the user (and any plugin running as that user) can write. A manual run uses the files in that folder, and `install-root.sh`'s failure trap runs `uninstall-root.sh` from the same folder as root. So whatever is in those files when the password is entered runs as root, and a file changed in between would run as root and, in the case of `fan-apply.py`, persist in `/etc/frame-fan`. The Framey App runs its install from a root-owned copy of the release it verified. Its Remove runs the copy of `uninstall-root.sh` built into the App, which is not a signed release. The README's Known limitations say what that does not cover. This trust boundary is documented here, not enforced by these scripts.

## Scripts

- `install-root.sh --signer-fp SHA256:...` (locked, `set -e`; exit 2 without the argument, exit 1 on a key mismatch, both before anything is changed): installs the trust file (see Updates), then runs `ff_install` from `root-lib.sh`: stops the path watcher, removes any old drop-in, copies Valve's `deckard-fan-control` directory to `/etc/frame-fan/fan`, installs `fan-apply.py`, the helper and the library, makes `/etc/frame-fan` root-owned and not group/other writable, writes the three units and the sudo rule, then applies the current settings if `fan.json` exists (otherwise restarts stock and records `{"stock": true}`). If applying them exits with an error because the file is stale or invalid, it runs `fan-apply.py --stock` instead, which records `{"stock": true, "fallback": true}`, and the install carries on; only a failing stock hand-over rolls the install back. It waits 15 seconds, requires `deckard-fan-control` to be active, enables the path watcher last and prints the fan RPM and `applied.json`. On any failure it runs the uninstall script as a rollback. The script traps INT, TERM and HUP to exit 1 after the EXIT trap is set, so a signal during the install also runs the uninstall. If applying the saved settings falls back to stock successfully, the install still completes, with the fallback flag recorded. It takes every file it uses from the folder it is run from, and never reads `/home/steamos/frame-fan` by path.
- `uninstall-root.sh` (locked, `set -e`): removes the sudo rule first, disables the path watcher, removes the units and the drop-in, reloads systemd, restarts the stock service, waits 3 seconds, requires it to be active, and removes `/etc/frame-fan` and `/var/lib/frame-fan` last. It stops at the first failing step, so a failure before the end leaves `/etc/frame-fan` in place. It does not touch `~/.config/frame-fan`.
- `selftest-root.sh` (takes no lock of its own; each `fan-apply.py` run it starts takes the shared lock; it runs for about 26 seconds): refuses to run unless it is root, `applied.json` exists and is a custom profile, and exactly one fan hwmon device is found. It then sends SIGKILL to the fan service 16 times at 1.4 second intervals to check the fallback, and checks that the fallback was recorded, the service is active, unit inspection succeeds and the unit no longer mentions `frame-fan`, and `pwm1` is readable. An exit trap (also on interrupt) clears the failed stock unit, reruns `fan-apply.py` and checks that the profile and an active service were restored. Each check prints `ok:` or `FAIL:`; the script ends with `PASS` and exit status 0, or `FAIL` and status 1 if any check failed or it was interrupted. It was checked only with stubbed commands, never on a headset.

## Offline checks

Run `python3 -B -m unittest discover -s tests -v` from the repository. The fixtures evaluate extracted ownership and tree predicates, selected apply functions and control flow with in-memory I/O, and extracted helper/library transitions with temporary paths and inert service/deletion substitutes. Real tar listing and Python hashing operate only on disposable fixtures. They cover failed unit inspection, prohibited links, throttle invalidation, duplicate skips, backup creation and refusal of missing/legacy/truncated/payload-corrupt backups before live deletion. They never launch the selftest, installer or update helper, and do not establish hardware, systemd, signature or installation behavior.

The apply script normalizes point coordinates to integers while parsing, then validates the normalized graph. Its sorted JSON request key is shared by the throttle comparison and the success stamp; only a successful restart permits that stamp. Before replacing custom state or handing over to stock, the apply script discards any old stamp. The root library also discards it before install reconstruction and activation; the helper does so before direct stock recovery and before a verified restore deletes live files, including restoration of a library from an older release. Uninstall clears it before removing the active units. A recent stamp therefore cannot suppress reapplication after those transitions, while ordinary duplicate requests for the still-active profile remain throttled. The page derives profile identity from the request projection, so saved names and status metadata do not affect acknowledgment or highlighting. The next custom name is the first unused `Custom N`; at most eight saved profiles means one of `Custom 1` through `Custom 9` is always available.
